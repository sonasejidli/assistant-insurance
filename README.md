# Insurance Assistant

An Azerbaijani question-answering application for exploring insurance documents. It searches local text and PDF files for relevant passages and uses an OpenRouter language model to generate answers based on those passages.

The included documents describe insurance legislation in Azerbaijan and are intended for testing. **This project is not a source of legal advice.** Check answers against authoritative, up-to-date sources.

## Features

- Browser interface and FastAPI endpoints.
- LangGraph retrieval runs query preprocessing, BM25, multilingual vector search, reciprocal rank fusion, cross-encoder reranking, and context selection before answer generation.
- Exact article lookup, insurance type/law/topic filters, and role-aware English/Azerbaijani query expansion.
- Optional Langfuse tracing for search and answer generation.
- Azerbaijani law-aware article and clause chunks, heuristic metadata, local cross-references, and separated editorial notes.
- Answers with cited law, article, and clause where available, and warnings for certain provisions delegating details to an executive authority.
- Selectable Azerbaijani, Russian, and English responses and topic prompts for exclusions, tariffs, claims, limits, rights and duties, comparisons, and scenarios.
- Clickable citations open indexed passages in a modal, with a PDF-page link when the page can be identified.
- An arithmetic-only percentage calculator and an in-browser, temporary history of recent questions.
- Docker Compose setup with a health check.

Only cited retrieved passages appear in `sources`. Citation labels are checked against retrieved passages, but this does not prove that the passages support every claim. Law names, numbers, articles, and clauses depend on heuristic extraction and may be absent or inaccurate. The executive-authority warning is also heuristic; it means the secondary regulation was not verified, not that an exhaustive search proved it absent.

The answer renderer supports `[S1]` source markers and full citations such as `[Law name, No. 250-IQ, Article 14, clause 14.5.1-1.9]` (the number is optional). Full citations are linked only when title, article, and clause uniquely match indexed metadata after case and whitespace normalization; unresolved or ambiguous references remain plain text. Clicking a link fetches the indexed passage, rather than text generated by the model. The index is built from extracted and cleaned document text, so its stored passage may not reproduce the original PDF verbatim; PDF links are shown only when the passage is uniquely located on a page.

## Requirements

- Docker and Docker Compose.
- An OpenRouter API key and a model available to your OpenRouter account.
- Internet access to build the image and to generate answers through OpenRouter.

## Getting Started

1. Create `App/.env` and add your own API key. Replace the placeholder; do not include quotes or commit the real key.

   ```dotenv
   OPENROUTER_API_KEY=your_openrouter_api_key
   LLM_MODEL=liquid/lfm-3-1.7b:free
   EMBED_MODEL=intfloat/multilingual-e5-large
   RERANK_MODEL=BAAI/bge-reranker-v2-m3
   ```

   `LLM_MODEL`, `EMBED_MODEL`, and `RERANK_MODEL` are optional; the values above are the defaults. The reranker is a separate, sizeable model and is downloaded during the Docker build. You can choose a different OpenRouter model if it is available to your account.

2. From the project root, build and start the application:

   ```sh
   docker compose --env-file App/.env up -d --build
   ```

   The first build downloads Python dependencies and the embedding model. Startup loads the model and indexes the text documents in memory, so it may take a little time.

3. Open `http://127.0.0.1:8002/` for the new frontend. The previous interface remains at `http://localhost:8000/`, with interactive API documentation at `http://localhost:8000/docs` and readiness at `http://localhost:8000/health`. Startup indexes the documents and can take several minutes; the frontend reports errors until the backend is ready.

The frontend is based on `sonasejidli/azeri-policy-compass` (commit `434996da242a4be005797f4ba1b065195dc541a5`). The landing page links to the live workspace, a sample dashboard, and preview-only sign-in and sign-up forms; account creation and authentication are not connected. The workspace uses the real assistant and passage-preview endpoints; the original prototype's simulated analytics and evaluation pages are not exposed in the integrated interface. Rebuild the frontend after changing its code with `docker compose --env-file App/.env up -d --build frontend`.

## Using the API

Send a question of 3-500 characters to `POST /ask`:

```json
{
  "question": "Which law sets the general framework for insurance contracts?"
}
```

The response contains an `answer`, a list of cited `sources`, and a list of `warnings`:

```json
{
  "answer": "Example answer. [S1]",
  "sources": [{"id": "S1", "document_number": 1, "doc": "law.txt", "law_name": "Insurance law", "law_number": "999-IIIQ", "article": "15-16", "clause": "15-16.0.4", "text": "Indexed source passage"}],
  "warnings": [],
  "disclaimer": "For informational purposes only; not legal advice. Verify the current law and consult a qualified professional.",
  "limits": [],
  "previews": [],
  "related_articles": []
}
```

If no sufficiently relevant information is found, or the model does not provide valid source labels, the application returns `Not found in the database.` with empty sources and warnings. An unavailable answer-generation service returns HTTP 503.

The model is instructed to produce short, direct sentences with source markers and no appended source list. Inline `[S1]`-style labels correspond to `id` in `sources`; each source represents a retrieved chunk, so multiple entries may reference the same document. Clicking a marker displays its metadata and indexed chunk text separately. That text may have been normalized during ingestion and is not guaranteed to match the original PDF verbatim. Invalid or missing citation IDs cause the answer to be rejected. The answer's structure and individual claims are model-generated and are not independently verified; check the cited sources.

Optional `/ask` fields are `language` (`auto`, `en`, `az`, or `ru`), `mode` (`question`, `exclusions`, `tariff`, `claims`, `limits`, `rights`, `comparison`, or `scenario`), and `history` (up to five prior question strings). By default `auto` asks the model to match the question's language. Localized fallback messages use a simple language heuristic, which can misidentify short or transliterated questions; select an explicit language when needed. `comparison` also requires `compare_laws`, an array containing two distinct, specific law names or numbers; the application retrieves each law separately and requires citations from both. Overlapping law filters are rejected. The browser keeps history in memory only, and the most recent prior question may be included in the next retrieval. History is sent to the model as context, not evidence. Clear it using the button or reload the page.

The answer stage starts with the selected reranked passages, removes duplicates, and can add adjacent continuations or resolved cross-references from the same indexed document. For a comparison, each available law gets an early slot. The prompt includes the available filename, PDF page, article, clause, and source references. Whole passages are packed before conversation history. `LLM_CONTEXT_WINDOW` (default `16384`) sets the application budget and `LLM_MAX_OUTPUT_TOKENS` (default `1536`) reserves room for generation. The application estimates prompt cost conservatively using UTF-8 byte length plus a message overhead allowance. Set both values within your provider's limits when changing models. [Default model limits](https://openrouter.ai/liquid/lfm-3-1.7b%3Afree)

The model labels inferences separately from quoted or paraphrased provisions, and every substantive statement carries a citation to a passage actually sent to the model. If the question is materially ambiguous, the API can return a targeted clarification with `intent: "clarification"`. If the evidence is incomplete, the API states that limitation and can return supported partial findings with citations. Citation checks validate passage IDs and placement. Whether a cited passage entails a model claim still requires review.

Topic modes are model instructions, not certified legal rules. The API's `limits` field extracts textual expressions from cited passages only, with surrounding context; it can miss or misclassify values and does not establish which limits apply. Rights descriptions and claims sequences depend on what the retrieved passages and model provide. Always check the source and its current version.

`previews` and `related_articles` contain links to indexed passages. Opening a preview shows its text and, if its full normalized text appears on exactly one extracted PDF page, a link to that page. Cross-page, repeated, OCR-altered, or otherwise unmatched text has no page link; no page is guessed. Preview and PDF endpoints are publicly accessible like the existing document endpoints.

For standalone arithmetic, send `{"base_azn": "11000", "rate_percent": "1"}` to `POST /calculate`. The result is `110.00` AZN. This only multiplies the user-supplied base and rate; it does not derive or validate legal rates, thresholds, eligibility, or tiered formulas. Consult cited provisions separately.

For retrieval without answer generation, send a request to `POST /search`:

```json
{
  "question": "What are the policyholder's obligations?",
  "filters": {"insurance_type": "medical", "law": "999-IIIQ", "topic": "deadline"},
  "limit": 5
}
```

All filters are optional and combine with AND. Insurance type matches extracted metadata; law matches the law name, number, or filename; topic is one of `tariff`, `exclusion`, and `deadline`. Topic matching uses the article title and text, so results depend on the source text and heuristic metadata. The same `filters` object is accepted by `POST /ask`.

Requests containing an article number such as `Article 20.0.2`, `Maddə 20.0.2`, or `20.0.2` perform exact lookup instead of semantic search. An explicit `"article": "20.0.2"` field also works with `/search` or `/ask`. `GET /articles/20.0.2` returns all matching chunks, with optional `insurance_type`, `law`, and `topic` query parameters. Specify a law to disambiguate provisions appearing in different laws or snapshots. A missing article does not fall back to unrelated results.

Lists such as `articles 1.1 and 2.1` are retrieved together, interleaving their matches. If any requested article is missing, exact lookup returns no matches. Standalone questions are searched independently. For a recognized follow-up, `/ask` and `/search` use one standalone rewrite for BM25, dense search, and reranking. The resolver uses at most one prior insurance question and asks for clarification if it cannot establish the reference. The answer model receives the original question and only the selected prior context, which is treated as untrusted. Query resolution can be audited in debug logs. An unresolved `/search` request returns `match_type: "clarification"`, an empty hit list, and the clarification question.

BM25 indexes normalized surface forms and adds recognized Azerbaijani lemmas on both queries and passages. The normalization preserves Azerbaijani letters and handles dotted and dotless I. The offline lemmatizer generates vowel-harmonized plural, possessive, and case combinations from a curated nominal lexicon. Unknown or ambiguous forms keep their surface tokens. Recognized ASCII spellings resolve only when they identify a unique lexicon entry. For retrieval, `hesablanma` also matches `hesablama` as an explicit equivalence.

Shared concept tokens connect Azerbaijani, English, and Russian aliases for terms such as premiums, payouts, and deductibles while keeping insurance roles distinct. Vector search embeds the natural-language query. Reciprocal rank fusion combines the two rankings, then the multilingual cross-encoder reorders the fused candidates. If the reranker fails, the service logs a warning and uses the fused order. Context selection takes the top reranked passages. The search score continues to report the highest cosine similarity among the selected passages. A matching insurance concept can also qualify selected passages for answer generation when the cosine score is low.

The library review found Azerbaijani language support in spaCy without a published pretrained pipeline and no Azerbaijani model in Stanza's published UD catalog. MorAz provides Azerbaijani-specific finite-state analysis through HFST and a Django service. The az-lang-nlp toolkit provides Azerbaijani stem and suffix analysis as a Go library. The built-in Python lemmatizer keeps processing local and deterministic for the supported insurance vocabulary. Its domain coverage is verified by regression tests and can be extended through the lemma lexicon. [spaCy language catalog](https://spacy.io/usage/models) · [Stanza model catalog](https://stanfordnlp.github.io/stanza/available_models.html) · [MorAz paper](https://aclanthology.org/D18-2005/) · [az-lang-nlp](https://github.com/az-ai-labs/az-lang-nlp)

Edit [the insurance terminology dictionary](App/config/insurance-terminology.json) to configure query expansion. Each entry in `concepts` has a stable ID and an `aliases` list for expressions that identify the same concept. Rules in `expressions` list colloquial `phrases` and candidate concept IDs with their cue phrases. Use an empty cue list for a single, unambiguous candidate. With `expand_when_unclear` enabled for a rule, conflicting cues keep each cued candidate and missing cues keep all configured candidates. Rules in `related_searches` add `concepts` when at least one phrase in every `requires` group appears within the same sentence or semicolon-delimited clause. An optional `alternatives` list identifies distinct interpretations that merit separate evidence.

BM25 uses the original query terms alongside the expansion concepts. Vector search and reranking use the original retrieval wording, including amounts, dates, and conditions. Indexed passages receive concept tokens from direct aliases. Candidate selection keeps a matching passage per plausible interpretation when the filters and result limit allow it. Set `expansion_enabled` to `false` to turn off contextual additions while retaining direct alias matching. Restart the backend after dictionary changes so it reloads the configuration and rebuilds the index.

BM25 and Qdrant run independently over passages that satisfy the same request filters. Each branch returns its own ranking. Weighted reciprocal rank fusion combines those lists before cross-encoder reranking. A passage may enter the pool through either branch.

| Environment setting | Default | Effect |
| --- | ---: | --- |
| `BM25_TOP_K` | 50 | Maximum lexical candidates |
| `VECTOR_TOP_K` | 50 | Maximum dense candidates |
| `VECTOR_SIMILARITY_THRESHOLD` | 0.0 | Minimum cosine similarity in Qdrant, from −1 to 1 |
| `BM25_WEIGHT` | 1.0 | Lexical contribution to rank fusion |
| `VECTOR_WEIGHT` | 1.0 | Dense contribution to rank fusion |
| `RRF_K` | 60 | Nonnegative rank constant for reciprocal rank fusion |
| `RERANK_TOP_K` | 24 | Fused candidates scored by the cross-encoder, increased when a request asks for more results |

Set these variables in `App/.env` or the API environment and restart the API. Candidate limits are independent of the final result limit. A zero weight excludes that branch from fusion. At least one weight must be positive. The vector similarity threshold applies only to semantic matches, so lexical matches can still reach reranking. The API reports the highest qualifying cosine similarity among the selected passages, or zero when none qualifies.

With default unit weights, RRF sums `1 / (RRF_K + rank)` across the two rankings, with ranks starting at 1. Configured weights scale each branch's term. The first occurrence of a document ID and chunk ID pair counts in each branch, and the fused list contains one entry per pair with its source metadata. Fusion uses rank positions only.

After RRF, `BAAI/bge-reranker-v2-m3` scores a shortlist against the same standalone query used for candidate retrieval. The shortlist keeps up to four leading candidates per active retrieval branch and fills the remaining slots from the fused ranking. The scoring input adds available insurance type, law name and number, chapter, section, article, and clause to the full passage. Candidates outside the shortlist keep their fused order. Only an article from the current request can trigger exact lookup. Docker Compose defaults to four OpenMP threads for CPU inference and accepts an `OMP_NUM_THREADS` override. [BAAI model card](https://huggingface.co/BAAI/bge-reranker-v2-m3)

Run `python evaluation/evaluate_reranker.py` to reproduce the Azerbaijani evaluation. On nine synthetic questions with three closely related candidates each, the relevant passage ranked first on 5/9 with RRF, 8/9 with the text-only cross-encoder, and 9/9 with the contextual cross-encoder. MRR was 0.778, 0.944, and 1.000 respectively. Law metadata resolved the case with identical wording in different insurance rules. This measures passage ordering within the labeled candidate sets. Production relevance remains unverified.

BM25 retains legal terms as surface tokens and adds distinct tokens for article and clause IDs, law numbers, amounts with currency, and percentages. Equivalent formats such as `5 000 manat` and `5000 AZN`, or `2,50 faiz` and `2.5%`, match the same value. Explicit article queries still use exact lookup.

Docker Compose runs Qdrant with a persistent `qdrant-storage` volume. For a standalone API, set `QDRANT_URL` and optionally `QDRANT_API_KEY` to use a server, or set `QDRANT_PATH` for a persistent local index in a single process. Without either setting, the API uses in-memory Qdrant. The collection name uses `QDRANT_COLLECTION` as a prefix and changes with the corpus, metadata, or embedding model. Startup reuses complete collections and leaves earlier versions available.

The existing PDF and text ingestion pipeline still preserves pages and legal hierarchy. It prefers sentence boundaries within a passage and uses `INDEX_CHUNK_CHARS` (default `1200`) as its character budget. The lexical and semantic branches run through LangGraph, followed by fusion, reranking, and evidence selection. Generation consumes the selected passages separately.

Before vector indexing, the active embedding tokenizer counts each full input, including the title, prefix, and special tokens. `EMBED_TARGET_TOKENS=0` uses the model's effective limit (512 for multilingual E5). A positive target can lower that budget. `EMBED_OVERLAP_TOKENS` defaults to 24 and caps the repeated context where a complete clause segment or word sequence fits. Oversized parents become vector-only child excerpts. The splitter prefers subsection, sentence, and semicolon boundaries and falls back to whole words when needed. It preserves each parent's page and legal metadata and logs old and new token counts, plus heuristic markers for legal information in the formerly omitted text. See the [embedding truncation evaluation](evaluation/embedding_truncation_report.md) for corpus results and target selection.

Qdrant ranks a parent by its best matching child. Parent IDs remain valid and each child records its offsets into the full passage. BM25, reranking, citations, and answer generation continue to use the complete parent passage. The passage encoder rejects input that would exceed the model limit.

The collection metadata records a SHA-256 fingerprint of the embedding configuration and the configuration itself. It includes the resolved model and tokenizer revision, tokenizer configuration, dimension, pooling, prefixes, normalization, input limit, relevant library versions, and chunking policy. Vector reuse requires the same fingerprint and the exact passage input. Identical inputs are encoded once, even when several passages retain distinct citations. The collection is usable after the indexer validates its configuration, vector dimensions, point IDs, and point fingerprints. Interrupted uploads in the same configuration resume from validated points.

The first startup with configuration fingerprints builds a new collection. Collections created by earlier code lack this provenance and are left intact while the corpus is re-encoded. A later configuration change also builds a separate collection, and the indexer leaves all previous collections available. Allow time for the first full reindex. For a deployment that must keep serving during the rebuild, validate the updated API against the shared Qdrant instance on a separate port before switching traffic.

Each payload includes the document and chunk IDs, filename and format, PDF page, section and article, original extracted text, and available chapter, clause, amendment-note IDs, and cross-references. Internal cross-references include the target chunk ID. PDF chunks stay on a single page while retaining legal hierarchy across page breaks. The preview opens the recorded page. Text files leave page numbers unset. When the parser cannot align a chunk to the extracted source text, the payload keeps the parsed text and records `original_text_verbatim: false`.

The default encoder is `intfloat/multilingual-e5-large`, evaluated in multilingual retrieval and on AZ-MIRAGE. Run `python evaluation/evaluate_embeddings.py` for the dense-only Azerbaijani insurance evaluation, or set `EMBED_MODEL=intfloat/multilingual-e5-base` to reproduce the comparator. On the synthetic insurance fixture, E5-large achieved Recall@3 / MRR@3 of 0.958 / 0.875 on 12 tuning queries and 0.875 / 0.875 on eight held-out queries. E5-base achieved 0.875 / 0.778 and 0.875 / 0.812 respectively. These results do not establish production retrieval quality. [Multilingual E5 technical report](https://arxiv.org/abs/2402.05672) · [AZ-MIRAGE results](https://github.com/LocalDoc-Azerbaijan/AZ-MIRAGE)

Run `python evaluation/tune_bm25.py` to reproduce the lexical-only grid search. The default settings are `k1=0.3` and `b=0`, selected by nDCG@3 on 12 labeled Azerbaijani tuning queries. Compared with the library defaults (`k1=1.5`, `b=0.75`), tuning nDCG@3 rose from 0.803 to 0.949 and recall@3 rose from 0.833 to 0.958. On eight held-out queries, recall@3 remained 1.000 and nDCG@3 fell from 1.000 to 0.954. The fixture uses synthetic insurance passages and hard negatives. These results measure lexical ranking on that fixture, and production ranking quality remains unverified.

`/search` returns chunks and metadata plus `match_type`. For hybrid search, `score` reports the maximum cosine similarity of the returned chunks. Exact lookup reports a null score. `/ask` passes usable retrieved passages to citation-checked generation. The vector branch still honors `VECTOR_SIMILARITY_THRESHOLD`.

Generated answers must use valid supplied source markers and cite each factual sentence. The service retries invalid output once with a shorter format and reports a temporary answer-service error if validation fails again. If the model explicitly reports no relevant evidence, the service returns the localized insufficient-evidence response. Citation validation checks structure and source IDs. Review the cited passages to verify what they support.

## Documents and Configuration

Place UTF-8 `.txt` or text-based `.pdf` documents in `data/index/`. The application builds an in-memory index on startup; no database or persistent version history is currently configured. PDF pages without extractable text are logged and skipped: run OCR externally before ingestion for scanned PDFs. Cleanup normalizes spaced Azerbaijani headings and joins wrapped lines; it does not run OCR or correct OCR recognition errors. Long passages preferentially split at sentence boundaries, with a word-boundary fallback for long sentences.

For legal texts, metadata and categories are inferred heuristically and may be missing or inaccurate. Cross-references link numbered provisions within the same document only, and unresolved targets have a null `target_chunk`. Editorial note definitions beginning with `[number]` are stored separately when present; references to missing notes remain as markers. The source document must actually contain the notes.

Use `GET /documents` to list indexed documents, `GET /documents/{name}/versions` to list supplied snapshots, and `GET /documents/{name}/versions/{filename}` to view their chunks, references, and notes. `{name}` is the filename stem before an optional `@` (for example, `law.txt` and `law@2020-01-01.txt` belong to `law`). These endpoints show supplied files only; amendment notes do not reconstruct past legal text. Versions are indexed independently and may both appear in search results.

Rebuild and recreate the container after adding or changing documents:

```sh
docker compose --env-file App/.env up -d --build
```

`EMBED_MODEL` selects the local multilingual sentence-transformer and `RERANK_MODEL` selects the local multilingual cross-encoder. For Hugging Face models, `EMBED_MODEL_REVISION` defaults to `main`. Startup resolves it to an immutable commit and loads both the model and tokenizer from that snapshot. Set it to a full commit hash in `App/.env` and rebuild to reproduce the same artifacts across image builds. Rebuild after changing either model so its weights are available in the offline runtime. The models are general-purpose multilingual models.

To opt in to metadata-only Langfuse tracing, set `LANGFUSE_TRACING_ENABLED=true`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY`, and optionally an HTTPS `LANGFUSE_BASE_URL` in `App/.env`. The exporter sends stage timings, scores, source IDs, and validation outcomes. It omits raw request and answer text. Configure project access and retention under the [observability deployment guidance](evaluation/platform_readiness.md#observability-and-privacy) before enabling export.

After changing other environment settings, recreate the container to load them:

```sh
docker compose --env-file App/.env up -d --force-recreate
```

To inspect logs or stop the application:

```sh
docker compose --env-file App/.env logs -f api
docker compose --env-file App/.env down
```

## Security and Privacy

- Keep `App/.env` and API keys private. The repository's `.gitignore` excludes environment files, but ignored files already tracked by Git remain tracked; check before pushing.
- Questions and retrieved document excerpts are sent to OpenRouter for answer generation. Do not use sensitive documents unless that data sharing is appropriate.
- No user authentication, role-based access control, administrative upload/re-index panel, audit log, or PII masking is implemented. Do not expose this service publicly or use it for sensitive information. Adding files and restarting the application remains a manual administrative operation.
- Feedback collection, a reviewed production golden-question dataset, and automated RAGAS evaluation are not implemented. Citation-label validation is not a factuality evaluation.
- The example texts are test material. Review both the documents and generated answers before relying on them.
